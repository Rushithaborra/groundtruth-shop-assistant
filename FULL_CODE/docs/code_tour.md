## 1. The path of one message

Take `cotton kurti 1500 ke andar`.

| Step | Where | What happens |
|---|---|---|
| 1. Load | `groundtruth/builder.py` `build_assistant` | Reads the catalogue and policy once. `catalogue/index.py` `CatalogueIndex` builds the vocabulary **from the catalogue itself**: product-type words, colours, materials, brands, attribute names. Only synonyms and Hinglish live in `resources/vocabulary.json`. |
| 2. Understand | `understanding/parser.py` `understand` | Turns the message into a `Parsed` (`understanding/parsed.py`): intents (price, stock, policy, ...), a search `Spec` (product type, filters, budget, size, sort), named product ids, and words it couldn't place (`unknown`). Here: material = cotton, the Kurtas category, budget under ₹1,500. Typos are matched only against catalogue words (`difflib`, cutoff 0.85, `index.py` `_closest`). No model is called. |
| 3. Decide | `answering/assistant.py` `_route`, then `_product_route` | Fixed order: reset, thanks, account questions (refused: we can't see orders), greeting, policy, then products. For products, `_compare_unsold_or_choice` handles two named products (compare), a brand the shop doesn't sell (refuse) and "A or B which is better" (clarify) before any search. |
| 4. Remember | `assistant.py` `_resolve` | Follow-ups refine the previous search ("1500 ke andar" keeps cotton kurti). Naming a new kind of product starts a fresh search. "Is it in stock?" after one product is about that product. |
| 5. Search | `catalogue/index.py` `search`, `rank` | Hard filters first: a product must match every filter and the budget. If description words find nothing, they are dropped and the reply says so (`relaxed`). Ranking: the asked-for sort, else in stock first, then word relevance, then rating. |
| 6. Answer, clarify or refuse | `assistant.py` `_search`, `_pick_one` | 0 hits: refuse with the closest cited alternative (`answering/refusals.py`). Several products that "the" product could be: ask which one, with no prices (`listings.clarify`). One product: its facts (`product_answers.product_answer`). Otherwise: a short listing. |
| 7. Write the reply | `answering/product_answers.py`, `listings.py`, `formatting.py` | Every sentence is built from catalogue fields and ends with its citation, e.g. `[SKU-...]`. **At the same time** the code records each claim in `Claims` (`answering/response.py`): cited ids, prices and facts, copied from the record, never read back out of the text. |
| 8. Check | `grounding/checker.py` `Grounding.check` | An independent re-check of the finished text against the raw records. Every citation exists; every ₹ amount is the price of the product cited beside it (or the shopper's own budget); every other number, product name, colour, material or brand comes from the cited record; policy sentences are word-for-word quotes. This is the badge in the demo, and the retailer view's "failed grounding check" count. |
| 9. Submit | `evaluation/submission.py` `prediction` | One JSON line per question, taken straight from `Response` and `Claims`. `main.py score` runs the organisers' own scorer on it. |

Policy questions take step 3's policy branch: `policy/sections.py` finds the sub-section by its words and
returns 1–2 sentences **verbatim**, cited as `[policy:1.1]`. If the question asks about something the policy never
mentions ("sunday delivery"), it says the policy is silent and quotes what it does say (`_policy`, `policy_silent`).

## 2. Why it can't invent a price

1. Prices are only ever written by code that reads `product.price` from the record it cites (`Claims.price`).
2. Nothing is generated by a model on the main path, so there is no free text to go wrong.
3. The checker independently ties every ₹ amount to the citation next to it. On all 190 pack questions: 0
   hallucinated prices and 0 replies flagged.

## 3. Questions judges are likely to ask

| Question | Answer | Point at |
|---|---|---|
| Why no LLM? | We measured the provided models instead of assuming: the embedding fallback lowered the dev score (0.92 against 1.00 on the tune half); the 0.5B model took 13.4 s a call and cut its JSON off. Rules take about 1 ms and invent nothing. The fallbacks are still in the code, with timeouts, retries and fall-back to rules. | `models/`, README "AI usage" |
| How do you know it doesn't lie? | Claims are recorded as they are written, then re-checked independently; the organisers' scorer agrees: 0 hallucinated prices. | `response.py` `Claims`, `checker.py` |
| What's your score? | Official scorer, dev questions we never tuned on: 0.900 (pack baseline 0.8275); all 40 dev: 0.950; real shoppers' first questions: 0.556 before we fixed what they showed. Small samples; the hidden test may be lower. | `main.py score --part check` |
| When does it refuse? | Products or brands the shop doesn't sell, facts the catalogue doesn't list ("missing is not no"), orders and accounts, policy topics the policy never mentions. | `refusals.py` |
| When does it ask instead? | When "the" product could be several products at different prices, or "A or B which is better" (the catalogue has nothing to judge "better" by). | `listings.py` `clarify`, `choice` |
| Hinglish and typos? | A Hinglish word list in `vocabulary.json`; typos are matched only against the catalogue's own words, so a typo can't turn into an invented product. | `parser.py`, `index.py` `_closest` |
| Multi-turn budget? | The session keeps type, filters, budget and sort; a follow-up refines them, a new kind of product starts over; "start over" clears it. | `assistant.py` `_resolve`, the "Remembered" panel |
| A new catalogue? | The vocabulary is built from the catalogue at load time; only synonyms and Hinglish are hand-written. | `index.py` `__init__` |
| Speed and cost? | Mean 0.6 ms a query, 0 model tokens; an LLM writing every reply is estimated at about 13.4 s and 3,950 tokens a query. | `main.py report` |
| Security? | Every API request is validated; same-site only; rate limits; security headers; replies are never rendered as HTML. | `api/validation.py`, `api/security.py` |
| What is it bad at? | Needs outside its hand-written map ("make my daily routine easier"); on wording it was never tuned on it scores about 0.73, and on need requests it never saw about 0.68. It refuses rather than guesses, so it stays honest, but it is less helpful there. Questions from real shoppers are the next step. | README Limitations, `main.py shoppers` |
| Who wrote what? | Both of us, with Claude Code; every commit and its author is in the README's pre-built-code table. | README |

## 4. Try it yourselves (20 minutes)

```bash
cd FULL_CODE
python3 main.py chat --catalogue data/pack/data/catalogue.jsonl --policy data/pack/data/policy.md --meta
```

Type these and say out loud which step in section 1 decided each reply:

1. `blue running shoes ka price` (clarify: several blue running shoes, different prices)
2. `cotton kurti for women`, then `1500 ke andar`, then `sabse sasti` (memory, then one product)
3. `havells table fan` (a brand the shop doesn't sell)
4. `chargit ripplezip black speaker paani me chalega?` (a fact the catalogue doesn't list)
5. `sunday delivery hogi?` (the policy is silent)
6. `start over`

Then break something on purpose: in `answering/product_answers.py`, change `format_inr(prod.price)` to
`format_inr(prod.price + 1)`, run `uv run python main.py score --part tune`, and watch the official scorer catch it:
one rupee off drops the score from 1.000 to 0.340, with 4 hallucinated prices (measured 29 October). Undo the edit
in your editor and run it again to see 1.000 come back. This is the best answer to "how do you know it doesn't
lie?": the scorer punishes a single wrong rupee, and ours has 0.
